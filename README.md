# Glitch Workshop — 2D Sokoban Puzzle

한 번 지나가면 굳어지는 **글리치 벽**, 박스를 건너편으로 보내는 **오버플로우 벽**, **단방향 포탈**을 활용하는 Unity 2D 소코반 퍼즐게임입니다.

박스를 목표 지점으로 밀어 넣으면서, 플레이어의 이동 경로와 기믹 사용 순서를 계획해야 합니다.

## 조작과 목표

| 입력           | 동작                  |
| ------------ | ------------------- |
| WASD / 방향키   | 상하좌우 한 칸 이동 및 박스 밀기 |
| R            | 현재 스테이지 재시작         |
| MAIN MENU 버튼 | 메인 메뉴 복귀            |

박스를 목표 지점에 밀어 넣으면 해당 박스가 사라집니다. 모든 박스를 처리하면 스테이지가 클리어됩니다.

목표 지점은 사라지지 않으므로 하나의 목표 지점에 여러 박스를 순서대로 넣을 수 있습니다.

## 주요 기믹

### 글리치 벽

- 플레이어만 통과할 수 있으며, 박스는 통과할 수 없습니다.
- 플레이어가 해당 칸을 벗어나면 일반 벽으로 굳어집니다.
- 통과한 길이 막히므로 이후 이동 경로까지 고려해야 합니다.

### 오버플로우 벽

- 플레이어는 통과할 수 없습니다.
- 박스를 밀어 넣으면 밀린 방향으로 연속된 오버플로우 벽을 건너뜁니다.
- 건너편 도착 칸에 박스를 놓을 수 없다면 밀기가 취소됩니다.

### 단방향 포탈

- 박스를 입구로 밀면 연결된 출구의 다음 칸으로 이동합니다.
- 나오는 방향은 박스를 밀었던 방향과 같습니다.
- 플레이어는 입구와 출구를 일반 바닥처럼 걸어 다닙니다.
- 박스는 포탈 출구 칸에 놓을 수 없습니다.
- 최종 도착 칸이 막혀 있으면 밀기가 취소됩니다.
- 연결된 입구와 출구는 같은 색상으로 표시합니다.

## 주요 구현

### 텍스트 기반 스테이지 생성

`LevelLoader`가 텍스트 파일의 문자를 읽어 타일과 오브젝트를 생성하고 좌표 정보를 저장합니다. 맵 텍스트를 수정하여 스테이지 구성을 변경할 수 있습니다.

| 문자       | 의미         |
| -------- | ---------- |
| `#`      | 일반 벽       |
| `.`      | 바닥         |
| `P`      | 플레이어 시작 위치 |
| `B`      | 박스         |
| `X`      | 목표 지점      |
| `G`      | 글리치 벽      |
| `O`      | 오버플로우 벽    |
| `1`\~`9` | 포탈 입구      |
| `a`\~`i` | 대응하는 포탈 출구 |

### 격자 좌표 기반 이동 판정

물리 충돌 대신 `Vector2Int` 좌표와 컬렉션을 사용하여 이동을 판정합니다.

박스를 미는 경우 도착 가능 여부를 먼저 검사하고, 이동이 가능하면 박스와 플레이어의 위치를 갱신합니다. 이후 플레이어가 벗어난 글리치 벽을 굳히고 클리어 여부를 확인합니다.

### 게임 상태와 스테이지 진행

- `Menu`, `Playing`, `Cleared` 상태에 따라 입력과 화면을 관리합니다.
- 게임 상태는 외부에서 읽을 수 있지만, 변경은 `GameManager` 내부에서 수행합니다.
- 처음에는 첫 스테이지만 열리며, 클리어하면 다음 스테이지가 열립니다.
- 잠긴 스테이지는 버튼을 비활성화하고, 진입 함수에서도 해금 여부를 검사합니다.
- 해금 기록은 `PlayerPrefs`로 저장하며, 이미 열린 스테이지는 재도전할 수 있습니다.
- 박스 위치 등 플레이 중간 상태는 저장하지 않습니다.

## 코드 구성

| 클래스                  | 주요 역할                                        |
| -------------------- | -------------------------------------------- |
| `PlayerController`   | 이동 입력, 이동 판정, 박스 밀기 및 기믹별 이동 처리              |
| `LevelLoader`        | 텍스트 맵 파싱, 오브젝트 생성, 좌표 데이터 관리, 박스 도착 가능 여부 검사 |
| `GameManager`        | 게임 상태, 목표 도착·클리어 처리, 메뉴 전환, 스테이지 해금·저장       |
| `PortalVisual`       | 연결된 포탈 쌍의 색상 표시                              |
| `PuzzlePresentation` | HUD, 카메라 화면 맞춤, 효과음 등 표현 요소                  |

핵심 로직의 참조 관계는 다음과 같습니다.

```text
PlayerController → GameManager
PlayerController → LevelLoader
GameManager      → LevelLoader
```

## 설계 및 문제 해결 경험

### 1. 좌표 자료구조의 선택

좌표의 존재 여부를 확인하는 데이터에는 `HashSet<Vector2Int>`를 사용했습니다. 일반 벽, 오버플로우 벽, 목표 지점, 유효한 타일 좌표 등이 해당합니다.

좌표와 함께 오브젝트 참조가 필요한 데이터에는 `Dictionary<Vector2Int, GameObject>`를 사용했습니다.

- **박스:** 이동 시 좌표 갱신, 목표 도착 시 오브젝트 삭제
- **글리치 벽:** 플레이어가 벗어나면 기존 오브젝트를 삭제하고 굳어진 벽으로 교체

조회 목적과 이후 수행할 작업에 따라 자료구조를 구분했습니다.

### 2. 포탈 연결 정보 표현

텍스트 맵에서 포탈의 입구·출구·연결 관계를 표현할 방법이 필요했습니다.

처음에는 홀수를 입구, 짝수를 출구로 사용하는 방식을 생각했습니다. 이후 AI와 설계 대안을 논의하면서 같은 문자를 사용하는 방식과 출구 방향 화살표 방식도 비교했습니다.

| 검토한 방식           | 고려한 점                                     |
| ---------------- | ----------------------------------------- |
| 홀수 입구·짝수 출구      | 인접한 숫자를 한 쌍으로 연결할 수 있지만 출구 방향은 별도로 결정해야 함 |
| 같은 문자 두 개        | 연결은 간단하지만 단방향 입구·출구를 구분할 추가 규칙이 필요함       |
| 출구 옆 방향 화살표      | 출구 방향을 지정할 수 있지만 화살표 탐색과 유효성 검사가 필요함      |
| **숫자 입구·소문자 출구** | 문자 종류로 역할을 구분하고 순서대로 짝을 연결할 수 있어 채택       |

최종적으로 `1 → a`, `2 → b`처럼 연결하고, 방향은 **박스를 밀었던 방향을 유지**하도록 선택해 직접 구현했습니다.

출구 다음 칸이 막혀 있으면 코드에서 밀기를 거부합니다. 출구 배치에 따라 가능한 진입 방향이 제한되므로 레벨 설계에서도 이를 고려했습니다.

이 방식은 맵 표현이 간단하지만 출구에서 이동 방향을 꺾는 퍼즐은 지원하지 않습니다.

### 3. 연속된 오버플로우 벽 처리

오버플로우 벽이 여러 칸 연속으로 배치된 경우에도 박스가 벽 구간을 모두 건너뛰도록 처리해야 했습니다.

도착 위치를 한 칸만 추가하는 방식으로 계산하면 다음 칸 역시 오버플로우 벽일 수 있습니다. 이를 처리하기 위해 `while`문으로 이동 방향의 연속된 오버플로우 벽을 탐색하고, 처음 만나는 다른 타일을 도착 후보로 정했습니다.

이후 `CanBoxLand()`로 해당 칸을 검사하여, 박스를 놓을 수 있을 때만 이동하도록 구성했습니다. 연속 구간의 끝을 찾는 것과 실제 착지 가능 여부를 분리했습니다.

| 배치                   | 기대 동작   |
| -------------------- | ------- |
| `박스 → O → O → 빈칸`    | 빈칸까지 이동 |
| `박스 → O → O → 일반 벽`  | 이동 거부   |
| `박스 → O → O → 다른 박스` | 이동 거부   |

### 4. 박스 도착 검사 공통화

일반 밀기·오버플로우·포탈은 이동 경로가 다르지만, 최종 도착 칸에 박스를 놓을 수 있어야 한다는 공통점이 있습니다.

이를 `CanBoxLand()`에서 검사하도록 구성했습니다.

- 맵에 존재하는 좌표인지
- 일반 벽·글리치 벽·오버플로우 벽인지
- 다른 박스가 있는지
- 포탈 입구 또는 출구인지

공통 조건을 한곳에서 관리하여 기믹별 검사 누락을 줄이고자 했습니다.

### 5. 여러 포탈 쌍의 시각적 구분

포탈을 여러 쌍 배치하면서 외형만으로 연결 관계를 구분하기 어렵다는 문제를 발견했습니다.

이를 개선하기 위해 연결된 입구와 출구에 같은 색상을 적용했습니다. 색상 처리 코드는 AI의 구현 도움을 받았으며, `MaterialPropertyBlock`으로 공통 머티리얼을 사용하는 포탈의 색상을 개별 설정합니다.

## 현재 지원 범위

- 이동 되돌리기는 지원하지 않으며, 진행이 막히면 현재 스테이지를 재시작해야 합니다.
- 포탈 출구 방향은 박스를 밀었던 방향을 따르며, 별도로 지정할 수 없습니다.
- 해금 기록만 저장하며, 진행 중인 스테이지의 배치는 저장하지 않습니다.
